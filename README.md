# business_family_control
# Техническое задание: Система для управления семейным бюджетом

## 1. Общие сведения

### 1.1. Наименование системы
Полное наименование: Автоматизированная система управления семейным бюджетом.
Сокращенное наименование: АСУ «Семейный бюджет» (или FamilyBudget).

### 1.2. Основание для выполнения работ
Проект выполняется в рамках семестровой работы по дисциплине Програмная инженерия (командный проект).

### 1.3. Цель выполнения работ
Целью работы является разработка и запуск веб-ориентированного программного обеспечения для учета, анализа и планирования доходов и расходов домохозяйства несколькими членами семьи в режиме реального времени.

### 1.4. Состав работ
В рамках проекта выполняются следующие этапы:
1. Проектирование архитектуры и базы данных системы.
2. Разработка клиентской и серверной частей веб-приложения.
3. Настройка и интеграция модулей системы.
4. Разработка пользовательской и технической документации.
5. Проведение тестирования и демонстрация работоспособности системы (защита).

---

## 2. Назначение системы

«Семейный бюджет» представляет собой единый цифровой ресурс для автоматизации учета финансовых потоков семьи. 

Система предназначена для:
* Автоматизации сбора и структурирования данных о доходах и расходах семьи;
* Разграничения прав доступа к финансовым данным для разных членов семьи;
* Анализа структуры трат и планирования лимитов (бюджетирования) по категориям;
* Формирования аналитической отчетности и графиков финансового состояния в режиме реального времени.

## 3. Описание услуги и сценарии использования

### 3.1. Схема предоставления сервиса
Пользователи (члены семьи) подключаются к веб-сервису через интернет с любого устройства (ПК, планшет, смартфон) через стандартный веб-браузер. Вычисления, обработка транзакций и хранение данных осуществляются на серверной стороне (Cloud / Backend) с базой данных.

### 3.2. Архитектура системы
Архитектура строится по клиент-серверной модели:
* **Frontend:** Веб-интерфейс пользователя (React).
* **Backend:** REST API сервер для обработки бизнес-логики и аутентификации.
* **Database (БД):** Реляционная база данных (PostgreSQL) для хранения профилей, транзакций и категорий.

### 3.3. Основные сценарии использования (Use Cases)

#### 3.3.1. Регистрация семьи и создание общего пространства
* **Действующие лица:** Пользователь (Глава семьи/Администратор).
* **Основные шаги:**
  1. Пользователь регистрируется в системе (указывает e-mail, имя, пароль).
  2. Создает семейную группу «Бюджет» и получает уникальный код/ссылку-приглашение.
  3. Отправляет ссылку другим членам семьи.

#### 3.3.2. Добавление/присоединение члена семьи
* **Действующие лица:** Член семьи, Администратор группы.
* **Основные шаги:**
  1. Член семьи переходит по ссылке-приглашению и проходит авторизацию.
  2. Вступает в семейную группу с ролью «Участник» или «Наблюдатель».

#### 3.3.3. Внесение доходов и расходов (Транзакций)
* **Действующие лица:** Член семьи.
* **Основные шаги:**
  1. Пользователь выбирает тип операции (Доход / Расход).
  2. Указывает сумму, дату, категорию (например, «Продукты», «ЖКХ», «Зарплата») и комментарий.
  3. Система сохраняет транзакцию и обновляет общий баланс семьи.

#### 3.3.4. Установка лимитов и планирование бюджета
* **Действующие лица:** Администратор группы.
* **Основные шаги:**
  1. Пользователь переходит в раздел «Категории».
  2. Устанавливает максимальный лимит трат на месяц для каждой категории.
  3. При приближении трат к лимиту система отображает предупреждающие индикаторы.

#### 3.3.5. Формирование аналитики и отчетов
* **Действующие лица:** Член семьи.
* **Основные шаги:**
  1. Пользователь выбирает отчетный период (месяц, квартал, год).
  2. Система формирует круговые диаграммы и графики динамики доходов/расходов.

## 4. Требования к системе

### 4.1. Функциональные требования

Система должна состоять из следующих функциональных модулей:

1. **Подсистема авторизации и аутентификации:**
   * Регистрация и вход по логину/e-mail и паролю.
   * Разграничение ролей (Администратор семьи, Член семьи).

2. **Подсистема управления семейным пространством:**
   * Создание и редактирование профиля семьи.
   * Генерация ссылок для приглашения новых участников.

3. **Подсистема учета транзакций:**
   * Создание, редактирование и удаление записей о доходах и расходах.
   * Гибкое управление категориями трат и поступлений (создание собственных категорий).

4. **Подсистема бюджетирования:**
   * Задание месячных лимитов по категориям.
   * Отображение прогресс-бара расхода средств.

5. **Подсистема аналитики и отчетности:**
   * Фильтрация событий по дате, категориям и авторам транзакций.
   * Визуализация данных (гистограммы, круговые диаграммы).

6. **Пользовательский веб-интерфейс:**
   * Рабочий стол (Дашборд) с текущим балансом и последними операциями.
   * Разделы: «Категории», «Бюджет», «Аналитика», «Семья».

---

### 4.2. Нефункциональные требования

#### 4.2.1. Требования к надежности и доступности
* Система должна обеспечивать корректную работу в режиме 24/7.
* Время отклика сервера на пользовательский запрос не должно превышать 2 секунд.
* Сохранность данных при сбоях должна обеспечиваться средствами транзакционности базы данных (ACID).

#### 4.2.2. Требования к информационной безопасности
* Пароли пользователей должны храниться в базе данных исключительно в хэшированном виде (например, bcrypt).
* Передача данных между клиентом и сервером должна осуществляться по защищенному протоколу HTTPS.
* Доступ к финансовым данным семьи должен предоставляться только авторизованным участникам этой группы.

#### 4.2.3. Требования к интерфейсу и совместимости
* Веб-интерфейс должен быть адаптирован для работы в популярных браузерах (Google Chrome, Mozilla Firefox, Yandex Browser, Safari).
* Интерфейс должен быть понятным, адаптивным и комфортным для работы как на ПК, так и на мобильных устройствах.

#### 4.2.4. Требования к программно-аппаратному обеспечению
* **Клиентская часть:** устройство с выходом в Интернет и установленным браузером.
* **Серверная часть:** минимальные характеристики виртуального сервера: 1 CPU, 2 ГБ RAM, 10 ГБ SSD.
* Интерфейс должен быть понятным, адаптивным и комфортным для работы как на ПК, так и на мобильных устройствах.

В рамках разработки с нуля выполняются следующие основные блоки работ:

2. **Разработка пользовательского интерфейса (Frontend):**
   * Создание адаптивного веб-интерфейса для ПК и мобильных устройств.

## 6. Состав и содержание работ по развертыванию (Инструкция по запуску)

Развертывание веб-сервера на ПК студента и преподавателя осуществляется через **Docker Compose**.

### 6.1. Предварительные требования

На компьютере должны быть установлены:

* **Git**
* **Docker Desktop** (включая Docker Engine и Docker Compose)

### 6.2. Порядок запуска проекта

1. **Клонирование репозитория:**
```bash
git clone https://github.com/your-username/business_family_control.git
cd business_family_control

```


2. **Настройка переменных окружения (при необходимости):**
Скопируйте пример файла конфигурации:
```bash
cp .env.example .env

```


3. **Сборка и запуск контейнеров:**
Выполните команду в корневой директории проекта:
```bash
docker compose up -d --build

```


4. **Проверка работы:**
После успешного запуска сервисов веб-интерфейс будет доступен в браузере по адресу:
`http://localhost:3000` (или `http://localhost:80`)
Серверный API доступен по адресу: `http://localhost:8000/api`
5. **Остановка сервисов:**
```bash
docker compose down

```

## 7. Порядок контроля и приемки

Для проверки корректности работы системы команда применяет комплексный подход, включающий модульное тестирование, интеграционное тестирование API и ручное тестирование пользовательских сценариев.

### 7.1. Определение штатного поведения ПО

Штатным признается поведение системы, при котором:

* Авторизованный пользователь может успешно добавлять транзакции со стандартными корректными значениями.
* Баланс семьи пересчитывается мгновенно и без ошибок.
* Графики аналитики корректно отображают внесенные данные.
* API возвращает статус-коды `200 OK`, `201 Created` при валидных запросах.

### 7.2. Определение и обработка внештатного поведения ПО

Система должна корректно обрабатывать и предотвращать следующие нештатные ситуации:

1. **Ввод невалидных данных:**
* *Ситуация:* Пользователь пытается ввести отрицательную сумму расхода, буквы в поле суммы или некорректную дату.
* *Реакция системы:* Форма блокирует отправку, пользователю выводится информативное сообщение об ошибке (валидация на клиенте и бэкенде, статус `400 Bad Request`).


2. **Несанкционированный доступ:**
* *Ситуация:* Пользователь пытается просмотреть данные чужой семейной группы по прямой ссылке.
* *Реакция системы:* Блокировка доступа, перенаправление на страницу ошибки или входа (статус `403 Forbidden` / `401 Unauthorized`).


3. **Сбой сети или недоступность БД:**
* *Ситуация:* Потеря соединения с сервером при отправке транзакции.
* *Реакция системы:* Интерфейс выводит уведомление о проблеме с сетью, данные формы не теряются, повторный запрос блокируется до восстановления связи.


4. **Параллельное редактирование:**
* *Ситуация:* Два члена семьи одновременно меняют настройки лимита одной категории.
* *Реакция системы:* Использование транзакций БД и блокировок для исключения состояния гонки (Race Condition).
